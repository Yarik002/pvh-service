Веб-приложение для учёта заказов и автоматизации работы пункта выдачи заказов (ПВЗ).

## 1. Назначение проекта

Приложение предназначено для автоматизации процессов приёмки, адресного хранения
и выдачи заказов в пункте выдачи заказов, а также для предоставления клиентам
возможности самостоятельно отслеживать статусы своих посылок.

Основные возможности (по техническому заданию):

* регистрация и авторизация пользователей с подтверждением Email;
* разграничение прав доступа по ролям `client` / `admin`;
* приёмка заказов с автоматическим или ручным назначением ячейки хранения;
* выдача заказов с освобождением ячейки;
* просмотр, фильтрация и сортировка списков заказов;
* адаптивная вёрстка и переключение светлой/тёмной темы.

## 3. Технологический стек

| Компонент | Технология | Обоснование |
|---|---|---|
| Среда выполнения | Node.js 20+ (проверено на 24.21.0) | единый язык JavaScript на клиенте и сервере |
| Веб-фреймворк | Express 4 | минималистичный, стандарт де-факто для REST API |
| СУБД | SQLite 3 (библиотека `better-sqlite3`) | требование ТЗ, п. 3.7; не требует установки сервера БД |
| Конфигурация | `dotenv` | настройки вынесены из кода в файл `.env` |
| Тестирование | встроенный модуль `node:test` | не требует дополнительных зависимостей |
| Пакетный менеджер | pnpm (совместим с npm) | быстрая установка, воспроизводимость через lock-файл |

Клиентская часть — адаптивная вёрстка на HTML5/CSS3 с JavaScript (без тяжёлых
фреймворков), разрабатывается с 9-го дня практики.

### 5.2 Запуск в контейнерах Docker

Проект можно запустить целиком в контейнерах — тогда Node.js и другие


Поднимаются два контейнера:

| Контейнер | Назначение | Адрес |
|---|---|---|
| `pvh-app` | сервер приложения | http://127.0.0.1:3000 |
| `pvh-mailpit` | перехватчик писем | http://127.0.0.1:8025 |

При первом запуске автоматически применяются миграции, создаётся учётная
запись администратора и справочник из 20 ячеек. Ответ сервера проверяется

Полезные команды:

```bash

```

#### Почему письма видны в mailpit, а не приходят на почту

По умолчанию письма принимает перехватчик внутри Docker. Это позволяет
проверить регистрацию и подтверждение адреса, **не заводя почтовый ящик**:
письмо видно в браузере по адресу http://127.0.0.1:8025, и при этом ничего
не уходит в интернет.

Проверка всей цепочки одной командой:

```bash
node scripts/check-docker-mail.js
```

Сценарий регистрирует пользователя, проверяет, что письмо принято почтовым
сервером, переходит по ссылке из письма и выполняет вход — 15 контрольных
точек.

#### Как включить отправку на реальную почту

Нужны настройки почтового сервера. Для Gmail это **пароль приложения**
из 16 букв; обычный пароль от почты не подойдёт — Gmail отклонит его
с ошибкой 535. Пароль создаётся на странице
[myaccount.google.com](https://myaccount.google.com) → *Безопасность* →
*Двухэтапная аутентификация* → *Пароли приложений*.

Затем создайте файл `.env.docker` (образец — `.env.docker.example`),
заполните его и раскомментируйте в `docker-compose.yml` две строки:

```yaml
    env_file:
      - .env.docker
```

Пример настроек для Gmail:

```
APP_BASE_URL=http://127.0.0.1:3000
MAIL_TRANSPORT=smtp
MAIL_FROM=erder101@gmail.com
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=erder101@gmail.com
SMTP_PASSWORD=пароль_приложения
```

Перед запуском полезно проверить настройки:

```bash
docker compose exec app node scripts/check-mail.js
```

Диагностика сообщит, пройден ли вход на почтовый сервер, и укажет причину
отказа: `530` — не указан логин, `535` — неверный пароль или использован
обычный пароль вместо пароля приложения.

> **Важно про ссылку в письме.** Адрес `APP_BASE_URL` подставляется в ссылку
> подтверждения. Пока приложение работает на локальном компьютере, ссылка
> вида `http://127.0.0.1:3000/...` откроется только на нём же. Для проверки
> с телефона или другого компьютера укажите в `APP_BASE_URL` адрес, доступный
> получателю.

| GET | `/health` | **основной эндпоинт приёмки:** состояние сервера и базы данных |

### 6.2 Регистрация пользователя

**`POST /api/auth/register`** — создание учётной записи с ролью `client`.

Тело запроса (JSON):

```json
{
  "name": "Иванов Иван",
  "email": "ivanov@mail.ru",
  "password": "parol12345",
  "passwordConfirm": "parol12345"
}
```

Правила проверки полей:

| Поле | Обязательное | Правила |
|---|---|---|
| `name` | да | от 2 до 100 символов, крайние пробелы удаляются |
| `email` | да | корректный формат, не более 254 символов, приводится к нижнему регистру, должен быть уникальным |
| `password` | да | от 8 до 128 символов, минимум одна буква и одна цифра; не должен входить в словарь часто используемых, содержать распространённые слова, повторы символов и личные данные пользователя |
| `passwordConfirm` | да | должен совпадать с `password` |

Требования к паролю проверяются в несколько этапов: сначала формат (длина,
состав символов), затем отсутствие повторов, затем отсутствие в словаре
ненадёжных паролей и, наконец, отсутствие личных данных пользователя.
Порядок выбран так, чтобы пользователь получал наиболее конкретную причину
отказа. Коды ошибок пароля: `TOO_SHORT`, `NO_LETTER`, `NO_DIGIT`,
`REPEATED_PATTERN`, `WEAK_PASSWORD`, `CONTAINS_COMMON_WORD`,
`CONTAINS_PERSONAL_DATA`.

Ответы:

| Статус | Когда возвращается |
|---|---|
| `201 Created` | пользователь создан |
| `400 Bad Request` | поля заполнены неверно; `error.details` содержит ошибку по каждому полю |
| `409 Conflict` | адрес электронной почты уже зарегистрирован |
| `429 Too Many Requests` | превышено число попыток (защита от перебора) |

Пример успешного ответа:

```json
{
  "success": true,
  "message": "Регистрация выполнена успешно. Подтвердите адрес электронной почты.",
  "user": {
    "id": 1,
    "name": "Иванов Иван",
    "email": "ivanov@mail.ru",
    "role": "client",
    "isConfirmed": false
  },
  "nextStep": "На адрес электронной почты будет отправлена ссылка для подтверждения аккаунта."
}
```

Пример ответа при ошибке валидации:

```json
{
  "success": false,
  "error": {
    "code": "BAD_REQUEST",
    "message": "Укажите корректный адрес электронной почты, например ivanov@mail.ru",
    "details": {
      "email": {
        "code": "BAD_FORMAT",
        "message": "Укажите корректный адрес электронной почты, например ivanov@mail.ru"
      }
    }
  }
}
```

### 6.3 Оценка надёжности пароля

**`POST /api/password/strength`** — оценка стойкости пароля с пояснением,
что следует улучшить. Эндпоинт не требует авторизации и используется
интерфейсом для подсказки пользователю при вводе пароля.

Тело запроса:

```json
{
  "password": "Xk9#mQ2$vL7p",
  "name": "Иванов Иван",
  "email": "ivanov@mail.ru"
}
```

Поля `name` и `email` необязательны: они позволяют проверить, не содержит ли
пароль личных данных пользователя.

Ответ (HTTP 200):

```json
{
  "success": true,
  "strength": {
    "score": 82,
    "level": "strong",
    "label": "Высокая",
    "color": "#388e3c",
    "checks": [
      { "id": "length", "title": "Длина не менее 8 символов", "passed": true, "advice": "" },
      { "id": "notCommon", "title": "Пароль отсутствует в списке часто используемых", "passed": true, "advice": "" }
    ],
    "warnings": []
  },
  "message": "Надёжность пароля: высокая (82 из 100)"
}
```

Оценка складывается из штрафов за конкретные недостатки, поэтому каждое
замечание сопровождается рекомендацией. Уровни надёжности: `veryWeak`
(менее 20 баллов), `weak` (до 55), `medium` (до 70), `strong` (до 85),
`veryStrong` (85 и выше).

Пароль не сохраняется и не записывается в журнал. Ограничение частоты
обращений настраивается переменной `PASSWORD_CHECK_MAX` (по умолчанию 200).

### 6.4 Отправка почты

Приложение отправляет письма двух видов:

| Письмо | Когда отправляется |
|---|---|
| Подтверждение адреса электронной почты | сразу после регистрации и при повторной отправке |
| Приёмка заказа (трек-номер и ячейка) | при приёмке заказа администратором (14-й день) |

**Режимы отправки** (параметр `MAIL_TRANSPORT`):

| Режим | Поведение |
|---|---|
| `log` (по умолчанию) | письмо выводится в журнал сервера. Позволяет проверить регистрацию и подтверждение адреса без реального почтового ящика |
| `smtp` | письмо отправляется через почтовый сервер по протоколу SMTP |

Режим `log` выбран значением по умолчанию осознанно: проект можно развернуть
и полностью проверить без настройки почтового сервера.

**Настройка реальной отправки.** В файле `.env` укажите параметры почтового
сервера и переключите режим:

```ini
MAIL_TRANSPORT=smtp
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=your-login@mail.ru
SMTP_PASSWORD=пароль-приложения
```

Для внешних почтовых сервисов требуется **пароль приложения**, а не пароль
от почтового ящика: обычный пароль сервис отклонит с ошибкой 535.

Проверить настройки без отправки письма:

```bash
npm run mail:check
```

Команда устанавливает соединение, проходит аутентификацию и выводит
поддерживаемые сервером возможности.

**Реализация SMTP-клиента.** Используется собственная реализация на встроенных
модулях `net` и `tls` (`src/mail/smtpClient.js`) вместо сторонней библиотеки:
для отправки писем достаточно небольшого набора команд протокола, а проект
не приобретает десятки лишних зависимостей. Поддерживаются неявное шифрование
TLS (порт 465), переход на TLS по команде STARTTLS (порт 587) и аутентификация
`AUTH PLAIN` и `AUTH LOGIN`.

Письмо формируется в формате MIME и содержит две части: обычный текст и HTML.
Тема письма кодируется по RFC 2047, поэтому кириллица отображается корректно
в любом почтовом клиенте. Текстовая часть обязательна: часть клиентов не
отображает HTML, а её наличие снижает вероятность попадания письма в «Спам».

### 6.5 Регистрация с подтверждением адреса электронной почты

**`POST /api/auth/resend-confirmation`** — повторная отправка письма со ссылкой
подтверждения. Используется, когда первое письмо не дошло: учётная запись уже
создана, а повторная регистрация на тот же адрес запрещена.

Тело запроса: `{ "email": "ivanov@mail.ru" }`

| Статус | Ситуация |
|---|---|
| `200 OK` | письмо отправлено повторно, сформирован новый токен |
| `400 Bad Request` | адрес не указан |
| `404 Not Found` | пользователь с таким адресом не найден |
| `409 Conflict` | учётная запись уже подтверждена |
| `429 Too Many Requests` | превышена частота запросов (не более 5 за 15 минут) |

Ответ регистрации дополнен блоком о результате отправки письма:

```json
{
  "success": true,
  "message": "Регистрация выполнена успешно. Проверьте почту и подтвердите адрес электронной почты.",
  "user": { "id": 1, "name": "Иванов Иван", "email": "ivanov@mail.ru", "role": "client", "isConfirmed": false },
  "passwordStrength": { "score": 82, "level": "strong", "label": "Высокая" },
  "confirmationEmail": { "sent": true, "status": "sent", "error": null },
  "nextStep": "Перейдите по ссылке из письма, чтобы активировать учётную запись."
}
```

**Ошибка отправки не отменяет регистрацию.** Учётная запись уже создана
в базе данных, поэтому откатывать операцию нельзя: пользователь получил бы
сообщение об ошибке, но не смог бы зарегистрироваться повторно (адрес занят).
В этом случае ответ содержит `"sent": false` и описание причины, а пользователь
может запросить письмо повторно.

### 6.6 Подтверждение адреса электронной почты

**`GET /api/auth/confirm?token=…`** — ссылка из письма. Открывается
в браузере, поэтому по умолчанию возвращается **HTML-страница** с понятным
результатом; при запросе с заголовком `Accept: application/json` возвращается
JSON.

| Статус | Ситуация | Что видит пользователь |
|---|---|---|
| `200` | адрес подтверждён или уже был подтверждён | страница об успехе с данными учётной записи |
| `400` | токен отсутствует или недействителен | страница с предложением запросить новое письмо |
| `410` | срок действия ссылки истёк | страница с предложением запросить новое письмо |

**`POST /api/auth/confirm`** — подтверждение с передачей токена в теле запроса
(`{ "token": "…" }`). Возвращает только JSON; удобно для программной проверки.

**`GET /api/auth/confirm/check?token=…`** — проверка ссылки **без** подтверждения
учётной записи. Позволяет интерфейсу заранее показать, действительна ли ссылка
и сколько времени осталось:

```json
{
  "success": true,
  "status": "valid",
  "message": "Ссылка действительна. Осталось времени: 23.9 ч.",
  "timeLeftHours": 23.9
}
```

**Свойства токена подтверждения:**

* формируется генератором `crypto.randomBytes` (32 байта, base64url);
* срок действия — 24 часа (настраивается `MAIL_CONFIRM_TTL_HOURS`);
* **одноразовый**: после успешного подтверждения очищается, поэтому повторный
  переход по ссылке не подтверждает учётную запись;
* дата формирования хранится в `confirm_token_created_at`, что позволяет
  проверять срок действия;
* при повторной отправке письма токен заменяется, а отсчёт срока начинается
  заново.

### 6.7 Вход в систему и сессии

**`POST /api/auth/login`** — вход по адресу электронной почты и паролю.

Тело запроса:

```json
{ "email": "ivanov@mail.ru", "password": "parol12345" }
```

| Статус | Ситуация |
|---|---|
| `200` | вход выполнен, выдан токен сессии |
| `400` | поля заполнены неверно |
| `401` | неверный адрес электронной почты или пароль |
| `403` | адрес электронной почты не подтверждён |
| `429` | превышена частота попыток входа |

Ответ:

```json
{
  "success": true,
  "message": "Вход выполнен успешно.",
  "token": "XKjVHNPsWgWtvqgL8qGTBqFIr-4C5uVQIIMtOBSvSP4",
  "tokenType": "Bearer",
  "expiresAt": "2026-10-08T07:02:56.000Z",
  "user": { "id": 1, "name": "Иванов Иван", "email": "ivanov@mail.ru", "role": "client", "isConfirmed": true }
}
```

**Токен выдаётся двумя способами одновременно:**

* в теле ответа — для программных клиентов и проверок;
* в cookie `pvh_session` с флагами `HttpOnly` и `SameSite=Lax` — для браузера,
  чтобы клиентский сценарий не имел доступа к токену.

**Передача токена при запросах.** Поддерживаются оба способа, приоритет
у заголовка:

```
Authorization: Bearer <токен>
Cookie: pvh_session=<токен>
```

**`GET /api/auth/me`** — данные текущего пользователя и сведения о сессии.
Требует действующей сессии, иначе `401`.

**`POST /api/auth/logout`** — выход из системы: текущая сессия завершается,
cookie удаляется. Повторный выход не считается ошибкой.

**`POST /api/password/change`** — смена пароля авторизованным пользователем.
После успешной смены **все прочие сессии завершаются**: если пароль изменён
из-за подозрения на компрометацию, доступ по старым токенам должен
прекратиться. Текущая сессия сохраняется.

**Свойства сессии:**

| Свойство | Реализация |
|---|---|
| Токен | 32 случайных байта, кодировка base64url |
| Хранение | в базе данных только хеш SHA-256 |
| Срок действия | 7 суток (`SESSION_TTL_HOURS`) |
| Завершение | удаление записи сессии (выход, смена пароля, удаление пользователя) |
| Учёт обращений | поле `last_used_at` обновляется при каждом запросе |

### 6.8 Роли пользователей и защита административных маршрутов

В системе две роли: **`client`** (получатель заказов) и **`admin`** (сотрудник
пункта выдачи). Роль хранится в поле `Users.role`, база данных не принимает
других значений.

Разграничение доступа выполняется middleware:

| Middleware | Назначение | Ответ при отказе |
|---|---|---|
| `requireAuth()` | требует действующую сессию | `401` |
| `requireRole('admin')` | требует роль администратора | `403` |
| `optionalAuth()` | определяет пользователя, если сессия есть | — |

Порядок проверок важен: сначала проверяется наличие сессии (`401`), затем
права (`403`). Так клиент, вошедший в систему, получает понятный отказ
«Недостаточно прав», а несостоявшийся пользователь — «Требуется авторизация».

**Разделение доступа к функциям:**

| Раздел API | Клиент | Администратор |
|---|---|---|
| `/api/auth/*` — регистрация, вход, профиль | да | да |
| `/api/password/*` — оценка надёжности, смена пароля | да | да |
| `GET /api/cells` — просмотр ячеек | да | да |
| `POST`, `PATCH`, `DELETE /api/cells` — изменение справочника | **403** | да |
| `/api/admin/*` — административный раздел | **403** | да |

### 6.9 Управление ячейками хранения

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /api/cells` | авторизованные | список ячеек со сводкой |
| `GET /api/cells/free` | авторизованные | только свободные ячейки и номер первой свободной |
| `GET /api/cells/summary` | авторизованные | сводка по складу без списка ячеек |
| `GET /api/cells/:id` | авторизованные | сведения об одной ячейке (администратор видит заказ в ней) |
| `GET /api/cells/suggest` | администратор | какая ячейка будет назначена заказу (ячейка не занимается) |
| `POST /api/cells` | администратор | добавить ячейку |
| `PATCH /api/cells/:id/status` | администратор | изменить состояние |
| `DELETE /api/cells/:id` | администратор | удалить ячейку |

Параметры запроса `GET /api/cells`:

| Параметр | Назначение |
|---|---|
| `status=Свободна` / `status=Занята` | фильтр по состоянию |
| `free=true` | только свободные ячейки |
| `withOrders=true` | добавить трек-номера заказов в ячейках (только для администратора) |

Пример ответа:

```json
{
  "success": true,
  "cells": [ { "id": 1, "cellNumber": 1, "status": "Свободна" } ],
  "summary": { "total": 20, "free": 18, "busy": 2, "occupancyPercent": 10,
               "firstFreeNumber": 3, "generatedAt": "2026-10-29T08:00:00.000Z" }
}
```

Ответ `GET /api/cells/free`:

```json
{
  "success": true,
  "cells": [ { "id": 3, "cellNumber": 3, "status": "Свободна" } ],
  "count": 18,
  "firstFreeNumber": 3,
  "message": "Свободных ячеек: 18. Первая свободная — № 3."
}
```

Если свободных ячеек нет, возвращается пустой список и `firstFreeNumber: null`:
это состояние склада, а не ошибка.

Особенности реализации:

* сводка считается одним запросом к базе, поэтому она всегда согласована:
  свободные + занятые = всего;
* ответы раздела не кешируются браузером (`Cache-Control: no-store`) —
  пользователь всегда видит актуальное состояние;
* клиент видит состояние ячеек, но не трек-номера и получателей чужих
  заказов: параметр `withOrders` и поле `order` учитываются только для
  администратора;
* идентификатор ячейки в адресе проверяется: `/api/cells/abc` → `400`
  с понятным сообщением, несуществующая ячейка → `404`;
* при добавлении ячейки номер можно не указывать — берётся следующий
  за наибольшим существующим;
* ячейку с активным заказом нельзя перевести в состояние «Свободна» —
  сначала оформляется выдача заказа (`409`);
* ячейку, на которую ссылаются заказы, нельзя удалить — возвращается `409`
  с указанием количества связанных заказов (ограничение внешнего ключа
  перехватывается до обращения к базе, чтобы сообщение было понятным).

### 6.9.1 Алгоритм назначения ячейки

Модуль `src/services/cellAssignment.js` выбирает ячейку для заказа
одним из двух способов (требование ТЗ, п. 3.6):

| Способ | Параметры | Какая ячейка выбирается |
|---|---|---|
| `auto` (по умолчанию) | — | первая свободная **по номеру** ячейки |
| `manual` | `cellId` или `cellNumber` | ячейка, выбранная администратором, если она свободна |

Отказы с понятными сообщениями:

| Код | Статус | Ситуация |
|---|---|---|
| `NO_FREE_CELLS` | 409 | свободных ячеек нет (или справочник пуст) |
| `CELL_BUSY` | 409 | выбранная ячейка занята; в ответе предлагается ближайшая свободная |
| `CELL_NOT_FOUND` | 404 | выбранной ячейки нет в справочнике |
| `CELL_REQUIRED` | 400 | при ручном выборе ячейка не указана |
| `INVALID_CELL` | 400 | ячейка указана не целым положительным числом |
| `INVALID_ASSIGN_MODE` | 400 | неизвестный способ выбора |

Функции модуля:

* `chooseCell()` — только находит ячейку, ничего не меняя (предварительный
  просмотр, адрес `GET /api/cells/suggest`);
* `occupyCell()` — занимает ячейку запросом `UPDATE … WHERE status = 'Свободна'`:
  если ячейку уже занял другой администратор, возвращается `409`, поэтому
  одна ячейка не может достаться двум заказам;
* `assignCell()` — выбор и занятие в одной транзакции; используется
  при приёмке заказа и откатывается вместе с ней при ошибке.

Пример: `GET /api/cells/suggest?mode=manual&cellNumber=5`, если ячейка 5 занята:

```json
{
  "success": false,
  "error": {
    "code": "CELL_BUSY",
    "message": "Ячейка № 5 занята. Ближайшая свободная — № 2.",
    "details": { "cell": { "code": "CELL_BUSY", "suggestedCellNumber": 2 } }
  }
}
```

### 6.9.2 Приёмка заказа

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/orders` | администратор | приёмка заказа: назначение ячейки и сохранение заказа |
| `GET /api/orders/:id` | авторизованные | заказ: администратор — любой, клиент — только свой (чужой → `404`) |

Тело запроса `POST /api/orders`:

```json
{
  "trackNumber": "RA123456789BY",
  "clientEmail": "ivanov@mail.ru",
  "description": "Книга, 0,5 кг",
  "cellMode": "auto"
}
```

| Поле | Обязательное | Правила |
|---|---|---|
| `trackNumber` | да | 6–40 символов: латинские буквы, цифры, дефис; приводится к верхнему регистру |
| `clientId` или `clientEmail` | одно из двух | получатель должен быть зарегистрирован и иметь роль `client` |
| `description` | нет | до 500 символов |
| `cellMode` | нет | `auto` (первая свободная, по умолчанию) или `manual` |
| `cellId` / `cellNumber` | при `manual` | выбранная ячейка должна быть свободна |

Порядок приёмки:

1. проверяются трек-номер, описание и получатель;
2. проверяется, что трек-номер ещё не принят (заказ «В пути» принимается —
   его статус меняется на «Готов к выдаче»);
3. **в одной транзакции** назначается ячейка (алгоритм 13-го дня) и
   сохраняется заказ со статусом «Готов к выдаче» и датой поступления;
4. клиенту отправляется письмо с трек-номером и номером ячейки.

Если любой шаг транзакции не удался, отменяются оба: не остаётся ни занятой
ячейки без заказа, ни заказа без ячейки. Ошибка отправки письма приёмку
не отменяет — посылка уже лежит в ячейке; результат отправки возвращается
в поле `notification`.

| Статус | Ситуация |
|---|---|
| `201` | заказ принят |
| `400` | неверный трек-номер, описание, получатель не указан или не клиент |
| `404` | получатель или выбранная ячейка не найдены |
| `409` | трек-номер уже принят (`TRACK_EXISTS`), заказ «В пути» другого клиента, ячейка занята, свободных ячеек нет |

### 6.9.4 Выдача заказа

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/orders/:id/issue` | администратор | выдача заказа клиенту |

В одной транзакции заказ переводится из «Готов к выдаче» в «Выдан» (ставится
дата выдачи), а его ячейка становится «Свободна». Номер ячейки остаётся
в заказе как история. Условие `status = 'Готов к выдаче'` в запросе не даёт
выдать заказ дважды.

| Статус | Ситуация |
|---|---|
| `200` | заказ выдан: `{ order, cell, message }` |
| `404` | заказ не найден |
| `409` | заказ уже выдан (`ORDER_ALREADY_ISSUED`) или ещё в пути (`ORDER_NOT_READY`) |

### 6.9.3 Списки заказов: «Мои заказы» и «Все заказы»

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `GET /api/orders/my` | авторизованные | заказы текущего пользователя |
| `GET /api/orders` | администратор | заказы всех клиентов (клиент получает `403`) |

Параметры строки запроса (все необязательные):

| Параметр | Значения | По умолчанию |
|---|---|---|
| `status` | `В пути`, `Готов к выдаче`, `Выдан` или `transit`, `ready`, `issued`, `all` | все статусы |
| `search` | часть трек-номера, описания, имени или адреса клиента (до 100 символов, регистр не важен) | — |
| `sort` | `receivedAt`, `issuedAt`, `trackNumber`, `status`, `cell`, `client` (только `/api/orders`) | `receivedAt` |
| `order` | `desc` (по убыванию) или `asc` (по возрастанию) | `desc` |
| `clientId` | заказы одного клиента (только `/api/orders`) | — |

Пример: `GET /api/orders/my?status=ready&sort=cell&order=asc`

```json
{
  "success": true,
  "orders": [
    {
      "id": 2, "trackNumber": "PVZ000000002", "description": "Наушники",
      "status": "Готов к выдаче", "receivedAt": "2026-10-03T12:00:00.000Z", "issuedAt": null,
      "client": { "id": 1, "name": "Иванов Иван", "email": "ivanov@mail.ru" },
      "cell": { "id": 1, "cellNumber": 1 }
    }
  ],
  "total": 1,
  "counts": { "all": 4, "inTransit": 1, "ready": 2, "issued": 1 },
  "filters": { "status": "Готов к выдаче", "search": "", "sort": "cell", "order": "asc" }
}
```

* `counts` — количество заказов по статусам без учёта фильтра: из них
  строятся счётчики на вкладках «Все / В пути / Готов к выдаче / Выдан»;
* статусы сортируются по жизненному циклу заказа (В пути → Готов к выдаче → Выдан),
  а не по алфавиту; заказы без даты (ещё «В пути») всегда в конце списка;
* поле сортировки не подставляется в SQL напрямую: берётся готовое выражение
  из списка допустимых, поэтому внедрение SQL через параметр невозможно;
* недопустимое значение параметра → `400` с кодом `BAD_FILTER` и указанием
  параметра в `error.details`.

### 6.9.5 Создание, изменение и удаление заказа, профиль (CRUD)

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/orders/expected` | администратор | ожидаемый заказ «В пути» (ячейка назначится при приёмке) |
| `PATCH /api/orders/:id` | администратор | изменение трек-номера, описания, получателя; выданный заказ не меняется (`409 ORDER_READONLY`) |
| `DELETE /api/orders/:id` | администратор | удаление заказа; ячейка заказа «Готов к выдаче» освобождается |
| `PATCH /api/auth/me` | авторизованные | изменение имени |
| `DELETE /api/auth/me` | авторизованные | удаление своей учётной записи, тело `{ password }` |
| `DELETE /api/admin/users/:id` | администратор | удаление учётной записи клиента |

Удалить учётную запись нельзя, пока в ячейках лежат её заказы
(`409 HAS_ACTIVE_ORDERS`), и нельзя удалить последнего администратора
(`409 LAST_ADMIN`). Сессии и заказы удаляются каскадно.

В интерфейсе: кнопки «Ожидаемый заказ», «Изменить», «Удалить» на странице
«Все заказы»; страница `/profile` (имя, смена пароля, удаление учётной записи);
кнопка «Удалить» у клиентов на странице администратора. Все удаления —
через окно подтверждения.

### 6.11.1 Тема оформления

Кнопка в шапке переключает три режима по кругу: **светлая → тёмная →
как в системе**. Выбор хранится в `localStorage` под ключом `pvh.theme`
и сохраняется после перезагрузки страницы.

| Режим | Значение `pvh.theme` | Что видит пользователь |
|---|---|---|
| Светлая | `light` | всегда светлая тема |
| Тёмная | `dark` | всегда тёмная тема |
| Как в системе | `system` (по умолчанию) | тема следует настройке операционной системы и меняется вместе с ней |

Особенности реализации:

* модуль `public/js/theme.js` подключён в `<head>` **без `defer` и до таблицы
  стилей** — тема выставляется до отрисовки страницы, поэтому при загрузке
  нет мерцания светлой темы;
* выбор, сделанный в одной вкладке, сразу применяется в остальных
  (событие `storage`);
* при переключении цвета меняются плавно, а пользователям, отключившим
  анимацию в системе, — мгновенно;
* контраст текста и фона в обеих темах не ниже 4,5:1 (рекомендация WCAG AA),
  это проверяется тестом `tests/theme.test.js`.

### 6.11.2 Страницы «Мои заказы» и «Все заказы»

Адрес `/orders`: клиент видит свои заказы, администратор — заказы всех
клиентов (пункт меню «Все заказы») с дополнительным столбцом «Клиент».

* вкладки «Все / В пути / Готов к выдаче / Выдан» со счётчиками из поля `counts`;
* поиск по трек-номеру и описанию (у администратора — и по клиенту),
  запрос отправляется через 0,3 с после окончания ввода;
* сортировка нажатием на заголовок столбца (повторное нажатие меняет
  направление, стрелка показывает текущее) или из списка «Сортировка»;
* фильтры сохраняются в адресе: `/orders?status=ready&sort=cell&order=asc`;
* клиент видит плашку «Заказ ждёт вас в пункте выдачи» с номерами ячеек;
* на телефоне таблица превращается в карточки с подписями значений.

Разметка — `src/views/ordersPage.js`, сценарий — `public/js/orders.js`.

### 6.11.2.1 Выдача заказа в интерфейсе

На странице «Все заказы» у заказов «Готов к выдаче» есть кнопка «Выдать».
Она открывает окно подтверждения (`<dialog>`) с крупным номером ячейки,
трек-номером, получателем и описанием. Фокус ставится на «Отмена»; Esc
закрывает окно. «Выдать заказ» отправляет `POST /api/orders/:id/issue`;
после выдачи показывается сообщение «ячейка № N свободна», список
обновляется. При отказе сервера окно не закрывается и показывает причину.
Сценарий — `public/js/orderActions.js`.

### 6.11.2.2 Автообновление статусов

Страница заказов сама опрашивает сервер каждые 15 секунд
(`public/js/ordersLive.js`). Если у заказа сменился статус или появился
новый заказ, строка подсвечивается и выводится сообщение, например
«Заказ PVZ100000001 — «Готов к выдаче», ячейка № 7». Пока вкладка скрыта,
опрос на паузе; при возврате список обновляется сразу. При ошибке сети
интервал растёт до 2 минут и возвращается к 15 секундам после успеха.
Индикатор «Обновлено в …» показывает время последнего обновления.

### 6.11.2.3 Уведомления и обработка ошибок

Все запросы к API проходят через `public/js/api.js`, где ошибки
перехватываются в одном месте (`handleGlobalError`):

| Ошибка | Что видит пользователь |
|---|---|
| сеанс завершён (401) | «Сеанс завершён» и переход на вход с возвратом на страницу |
| нет прав (403) | «Недостаточно прав» |
| слишком много запросов (429) | «Слишком много запросов» |
| ошибка сервера (5xx) | «Ошибка сервера», без технических подробностей |
| нет сети, тайм-аут | «Нет связи с сервером» |
| ошибки полей (400, 404, 409) | сообщения у полей формы |

Уведомления (`PVH.toast`) появляются в правом нижнем углу, закрываются
сами или кнопкой ×, ошибки объявляются программам чтения с экрана.
Фоновые запросы автообновления уведомлений не показывают.

### 6.11.3 Оформление интерфейса

Идея оформления — склад и почтовая маркировка: тёплый «бумажный» фон,
чёрные кнопки, сигнальный жёлтый цвет и лента разметки, моноширинный шрифт
для трек-номеров. Шрифты Onest, Unbounded и JetBrains Mono (кириллица)
подключаются с Google Fonts; без интернета используются системные шрифты.
На главной странице — схема стеллажа с реальной занятостью ячеек.
Контраст текста в обеих темах не ниже 4,5:1 (проверяется тестами).

### 6.11.4 Страница «Приёмка товара»

Страница `/receive` (только администратор) оформляет поступившую посылку
через запрос `POST /api/orders`:

1. администратор вводит трек-номер и получателя — при вводе адреса появляется
   список зарегистрированных клиентов;
2. при необходимости указывает описание (счётчик «N из 500 символов»);
3. выбирает ячейку: **автоматически** (первая свободная) или **вручную**
   из списка свободных; ячейка, которая будет назначена, показывается
   до отправки формы;
4. нажимает «Принять посылку» — номер ячейки показывается крупно, внизу
   отображается результат отправки письма клиенту и список «Принято за сеанс»;
   форма очищается для следующей посылки, список ячеек обновляется.

Ошибки выводятся у полей формы: неверный или уже принятый трек-номер —
у трек-номера, незарегистрированный получатель — у получателя, занятая
ячейка — у списка ячеек. Если свободных ячеек нет, кнопка приёмки
отключается с пояснением.

## 7. База данных

Схема создаётся автоматически при первом запуске сервера из файлов миграций
в каталоге `src/db/migrations`:

| Миграция | Содержание |
|---|---|
| `001_initial_schema.sql` | таблицы `Users`, `Storage_Cells`, `Orders`, индексы, триггер, 20 ячеек |
| `002_users_password_fields.sql` | поля `password_changed_at` (дата смены пароля) и `must_change_password` |

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `Users` | пользователи системы | уникальный Email, роль `client`/`admin`, признак подтверждения, хеш пароля, токен подтверждения, дата смены пароля |
| `Storage_Cells` | ячейки хранения | уникальный номер, статус «Свободна»/«Занята» |
| `Orders` | заказы (посылки) | уникальный трек-номер, статус, внешние ключи на пользователя и ячейку |

Хранение паролей:

* в поле `password_hash` записывается результат работы функции `scrypt`
  со случайной солью в формате `scrypt$N$r$p$<соль>$<хеш>`;
* пароль в открытом виде не сохраняется ни в базе данных, ни в журналах;
* проверка пароля выполняется сравнением за постоянное время
  (`crypto.timingSafeEqual`), чтобы исключить атаки по времени;
* поле `password_changed_at` заполняется при каждой смене пароля;
* поле `must_change_password` предназначено для принудительной смены пароля
  (например, при сбросе администратором).

Реализованные ограничения целостности:

* внешние ключи с правилами `ON DELETE CASCADE` (пользователь → заказы)
  и `ON DELETE RESTRICT` (ячейка → заказы);
* `CHECK`-условия на формат Email, длину имени, допустимые значения ролей и статусов;
* согласованность статуса и даты выдачи заказа;
* частичный уникальный индекс `ux_orders_active_cell` — одна ячейка обслуживает
  не более одного активного заказа;
* триггер `trg_orders_free_cell_on_delete` — освобождение ячейки при удалении заказа.

При создании базы данных автоматически добавляются 20 ячеек хранения.

Управление схемой:

```bash
npm run db:migrate           # применить новые миграции
node scripts/migrate.js status   # показать состояние миграций
npm run db:reset             # пересоздать базу данных (с подтверждением)
```

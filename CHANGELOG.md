# Журнал изменений проекта

Формат записей основан на принципах Keep a Changelog.
Версии соответствуют сборкам, описанным в плане практики.

## [0.3.0] — 4-й день практики

### Добавлено

**Оценка надёжности пароля**
* `src/data/commonPasswords.js` — словарь часто используемых паролей
  (более 100 записей: цифровые последовательности, «клавиатурные» пароли
  в латинской и русской раскладках, словарные слова, имена) и список
  распространённых слов для поиска внутри пароля.
* `src/utils/passwordStrength.js` — оценка стойкости пароля от 0 до 100 баллов
  с пояснением по каждому пункту. Реализованы проверки: длина, разнообразие
  типов символов, отсутствие в словаре часто используемых паролей, отсутствие
  распространённых слов, отсутствие личных данных пользователя, отсутствие
  повторов и «клавиатурных» последовательностей.
* Распознавание «замаскированных» паролей: нормализация регистра и разделителей,
  расшифровка замен символов (`p@ssw0rd` → `password`), отбрасывание цифр
  в конце (`qwerty2026` → `qwerty`).
* `src/validators/passwordRules.js` — правила проверки пароля
  (`notCommonPassword`, `noCommonWord`, `noRepeatedPattern`, `noPersonalData`).

**Смена пароля**
* `src/services/passwordService.js` — смена пароля с проверкой текущего пароля
  и оценкой надёжности нового; проверка надёжности пароля по запросу.
* `src/db/migrations/002_users_password_fields.sql` — поля
  `password_changed_at` и `must_change_password` в таблице `Users`.
* `userRepository.updatePasswordHash()` и `updateConfirmToken()`.

**REST API**
* `POST /api/password/strength` — оценка надёжности пароля с рекомендациями
  (доступна без авторизации, ограничена по частоте обращений).
* Ответ регистрации дополнен блоком `passwordStrength` с оценкой принятого пароля.
* Правило `differsFrom()` — новый пароль не должен совпадать с текущим.

**Проверка и документация**
* `scripts/check-v0.3.js` — автоматическая проверка сборки по 30 контрольным точкам.
* `tests/passwordStrength.test.js` — 18 тестов оценки надёжности пароля.
* `tests/passwordChange.test.js` — 12 тестов смены пароля.
* `docs/postman/PVZ-Password-Day4.postman_collection.json` — коллекция из 7 запросов
  с автоматическими проверками.

### Изменено

* Версия сборки повышена до 0.3.0; `npm run check` выполняет проверку текущей
  сборки, проверки предыдущих дней доступны командами `npm run check:v01`
  и `npm run check:v02`.
* `userRepository.toPublic()` теперь удаляет и хеш пароля, и токен подтверждения:
  ранее хеш мог попасть в ответ сервиса.
* Проверка пароля на личные данные перенесена в сервисный слой: при смене пароля
  имя и адрес берутся из записи пользователя, а не из формы.

### Технические решения

* Оценка надёжности построена на штрафах за конкретные недостатки, а не на едином
  регулярном выражении: это позволяет объяснить пользователю, что именно следует
  исправить, и подготовить основу для индикатора надёжности в интерфейсе (10-й день).
* Словарь ненадёжных паролей хранится в нормализованном виде, а сравнение
  выполняется по нескольким вариантам написания — это позволяет распознавать
  пароли вида «Qwerty_123», «P@ssw0rd», «qwerty2026» без увеличения словаря.
* Маршрут смены пароля `POST /api/password/change` будет подключён на 7-м дне,
  после реализации авторизации: до этого момента операция недоступна по HTTP,
  так как изменять пароль без подтверждения личности небезопасно.

## [0.2.0] — 3-й день практики

### Добавлено

**Валидация данных**
* `src/validators/rules.js` — набор правил проверки значений: обязательность
  заполнения, длина, формат адреса электронной почты (регулярное выражение),
  сложность пароля, совпадение с другим полем, вхождение в список допустимых.
* `src/validators/schemas.js` — схема проверки формы регистрации.
* Функция `validate()` собирает ошибки по всем полям сразу и выбрасывает
  прикладную ошибку 400 с перечнем ошибок в `error.details`.

**Безопасность**
* `src/utils/password.js` — хеширование паролей функцией `scrypt` из встроенного
  модуля `node:crypto` со случайной солью; проверка пароля сравнением за
  постоянное время (`timingSafeEqual`). Формат записи: `scrypt$N$r$p$соль$хеш`.
* `src/utils/token.js` — генерация криптографически стойких токенов
  (`randomBytes`) для подтверждения Email и будущих сессий.
* `src/middleware/rateLimit.js` — ограничение частоты запросов (защита от
  перебора) с информационными заголовками `X-RateLimit-*` и `Retry-After`.
* Пароль в открытом виде не сохраняется и не возвращается клиенту;
  хеш пароля и токен подтверждения не покидают сервер.

**Слой доступа к данным и бизнес-логика**
* `src/repositories/userRepository.js` — операции с таблицей `Users`:
  поиск по идентификатору, адресу электронной почты и токену подтверждения,
  создание пользователя, подтверждение учётной записи.
* `src/services/authService.js` — регистрация пользователя: проверка полей,
  контроль уникальности адреса электронной почты, формирование хеша пароля,
  сохранение записи со статусом «не подтверждён» и токеном для письма.

**REST API**
* `src/routes/auth.js` — эндпоинт `POST /api/auth/register`:
  201 при успехе, 400 при ошибках валидации, 409 при повторной регистрации,
  429 при превышении частоты запросов.
* Префикс `/api` подключён к приложению; корневой маршрут `/` дополнен
  перечнем реализованных и запланированных эндпоинтов.
* Метод `AppError.tooManyRequests()` — прикладная ошибка 429.

**Проверка и документация**
* `scripts/check-v0.2.js` — автоматическая проверка сборки по 22 контрольным
  точкам (успешная регистрация, дубликаты, регистр адреса, пустая форма,
  пять вариантов неверного Email, короткий пароль, пароль без цифр,
  несовпадение паролей, короткое имя, формат хранения пароля, защита
  от перебора, работоспособность `/health`).
* `scripts/run-tests.js` — запуск всех модульных тестов проекта.
* `tests/validation.test.js` — 11 тестов правил валидации.
* `tests/password.test.js` — 7 тестов хеширования паролей.
* `tests/auth.test.js` — 10 тестов сервиса регистрации.
* `docs/postman/` — коллекция запросов Postman (7 запросов с автоматическими
  проверками) и окружение для проверки API вручную.

### Изменено

* Версия сборки повышена до 0.2.0; сценарий `npm run check` выполняет проверку
  текущей сборки, проверка 2-го дня доступна командой `npm run check:v01`.
* Пределы частоты запросов вынесены в переменные окружения
  `RATE_LIMIT_WINDOW_MS` и `RATE_LIMIT_MAX`.

### Технические решения

* Для хеширования выбран `scrypt` из встроенного модуля `node:crypto`, а не
  библиотеки `bcrypt` или `argon2`: они требуют компиляции нативных модулей,
  что усложнило бы развёртывание проекта на другом компьютере.
* Ограничение частоты запросов реализовано в памяти процесса без внешнего
  хранилища: для учебного проекта этого достаточно. При развёртывании на
  нескольких серверах потребовалось бы общее хранилище (например, Redis).

## [0.1.0] — 2-й день практики

### Добавлено

**Инфраструктура проекта**
* Репозиторий Git инициализирован, настроен файл `.gitignore`.
* Файл `package.json` с описанием проекта, перечнем зависимостей и сценариями запуска.
* Файл `.env.example` — образец настроек окружения (порт, путь к БД, уровень логирования).
* Файл `pnpm-workspace.yaml` с настройкой `nodeLinker: hoisted` для корректной
  работы `node_modules` в Windows.

**Подключение базы данных SQLite**
* `src/db/connection.js` — единое соединение с БД (паттерн Singleton), PRAGMA
  `foreign_keys`, `journal_mode = WAL`, `busy_timeout`, функция `ping()` для проверки
  доступности, вспомогательная функция `transaction()`.
* `src/db/migrate.js` — собственный механизм миграций с учётом применённых
  скриптов в таблице `schema_migrations`; каждая миграция выполняется в транзакции.
* `src/db/migrations/001_initial_schema.sql` — схема базы данных, спроектированная
  на 1-й день: таблицы `Users`, `Orders`, `Storage_Cells`, четыре индекса, частичный
  уникальный индекс активной ячейки, триггер освобождения ячейки и 20 стартовых ячеек.

**Каркас сервера**
* `src/config/index.js` — централизованное чтение конфигурации с проверкой типов.
* `src/utils/logger.js` — логгер с уровнями `error`/`warn`/`info`/`debug`.
* `src/utils/AppError.js` — класс прикладной ошибки с HTTP-статусом и статическими
  фабриками (`badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`,
  `unavailable`).
* `src/middleware/requestLogger.js` — журналирование запросов с длительностью обработки.
* `src/middleware/errorHandler.js` — обработчики 404 и централизованный обработчик
  ошибок, единый JSON-формат ответа об ошибке.
* `src/routes/health.js` — эндпоинты `/health`, `/health/live`, `/health/ready`.
* `src/app.js` — сборка приложения Express: разбор JSON, логирование, заголовки
  безопасности, статика, корневой маршрут, заготовка префикса `/api`.
* `src/server.js` — точка входа: подготовка БД, применение миграций, запуск
  HTTP-сервера, корректная остановка по `SIGINT`/`SIGTERM`, обработка
  `uncaughtException` и `unhandledRejection`.

**Вспомогательные сценарии**
* `scripts/setup.js` — первоначальная настройка проекта: проверка версии Node.js,
  создание файла `.env`, проверка зависимостей, создание базы данных, применение
  миграций и контрольная проверка сборки (команда `npm run setup`).
* `scripts/migrate.js` — применение миграций и вывод их состояния (`status`).
* `scripts/reset-db.js` — полное пересоздание базы данных с подтверждением.
* `scripts/check-v0.1.js` — автоматическая проверка сборки по 11 контрольным точкам.
* `scripts/archive-day.js` — создание снимка исходного кода в архив дня практики.

**Тестирование**
* `tests/smoke.test.js` — 4 модульных теста каркаса на встроенном модуле `node:test`.

**Документация**
* `README.md` — назначение, стек, структура, инструкция по установке и запуску,
  описание эндпоинтов, схемы БД и настроек.
* `CHANGELOG.md` — журнал изменений по дням практики.
* Отчёт о работе за день в формате DOCX с титульным листом
  (`Разработка\день 2\Отчет_день_2_каркас_сервера_и_SQLite.docx`).

### Результат дня

Критерий приёмки выполнен: **сборка v0.1 — сервер запускается, эндпоинт `/health`
возвращает OK.**

```
Всего проверок: 11, пройдено: 11, ошибок: 0
```

### Технические решения

* Выбрана библиотека `better-sqlite3`, а не `node:sqlite`: она предоставляет
  синхронный API и готовые бинарные сборки (N-API prebuilds), поэтому установка
  не требует компилятора C++ и работает на Node.js 20 и выше.
* Механизм миграций написан самостоятельно вместо подключения ORM: весь SQL
  остаётся видимым и проверяемым, что важно для защиты учебного проекта.
* Логгер и middleware журналирования реализованы без сторонних библиотек
  (`morgan`, `winston`) — меньше зависимостей, полный контроль над форматом вывода.

## [0.0.1] — 1-й день практики

### Добавлено

* Проектирование архитектуры базы данных: три связанные таблицы `Users`,
  `Orders`, `Storage_Cells`.
* SQL-скрипт `schema.sql`, создающий базу данных без ошибок (проверен
  выполнением в SQLite).
* Ограничения целостности: внешние ключи, `CHECK`-условия на значения
  перечислений, частичный уникальный индекс на активную ячейку, триггер
  автоматического освобождения ячейки.

# Журнал изменений проекта

Формат записей основан на принципах Keep a Changelog.
Версии соответствуют сборкам, описанным в плане практики.

## [0.12.0] — 13-й день практики

### Добавлено

**Алгоритм назначения ячейки**
* `src/services/cellAssignment.js` — выбор ячейки хранения для заказа:
  * `auto` — первая свободная ячейка по номеру (а не по идентификатору:
    номер написан на самой ячейке);
  * `manual` — ячейка, выбранная администратором по идентификатору или номеру,
    с проверкой, что она существует и свободна.
* Понятные отказы с кодами: `NO_FREE_CELLS` (свободных нет), `CELL_BUSY`
  (выбранная занята — в ответе предлагается ближайшая свободная),
  `CELL_NOT_FOUND`, `CELL_REQUIRED`, `INVALID_CELL`, `INVALID_ASSIGN_MODE`.
* Разделение выбора и занятия: `chooseCell()` ничего не меняет,
  `occupyCell()` занимает ячейку условным запросом, `assignCell()` выполняет
  оба шага в одной транзакции (понадобится при приёмке заказа).
* `GET /api/cells/suggest?mode=auto|manual` — предварительный выбор ячейки
  для администратора; ячейка при этом не занимается.

**Проверка и документация**
* `scripts/check-v0.12.js` — автоматическая проверка сборки по 27 контрольным
  точкам: склад заполняется до последней ячейки, затем ячейка освобождается.
* `tests/cellAssignment.test.js` — 20 тестов алгоритма и адреса `/suggest`.

### Технические решения

* Ячейка занимается запросом `UPDATE … SET status = 'Занята' WHERE id = ?
  AND status = 'Свободна'`. Если между выбором и занятием ячейку занял
  другой администратор, запрос не изменит ни одной строки — возвращается
  отказ `409`, и ячейка не достаётся двум заказам.
* `assignCell()` использует транзакцию; внутри внешней транзакции приёмки
  она становится точкой сохранения, поэтому сбой приёмки отменяет и занятие
  ячейки. Это проверяется тестом.
* Отсутствие свободных ячеек — ответ `409 Conflict`, а не `404`: запрос
  корректен, но не может быть выполнен из-за текущего состояния склада.

## [0.11.0] — 12-й день практики

### Добавлено

**API управления ячейками**
* `GET /api/cells/free` — только свободные ячейки, отсортированные по номеру,
  их количество и номер первой свободной. Если свободных нет — пустой
  список и `firstFreeNumber: null` (это состояние склада, а не ошибка).
* `GET /api/cells/summary` — сводка по складу без списка ячеек: всего,
  свободно, занято, заполненность, первая свободная, время формирования.
* В сводку `GET /api/cells` добавлены поля `firstFreeNumber` и `generatedAt`.
* `GET /api/cells/:id` для администратора содержит поле `order` — заказ
  в ячейке, его описание, дата поступления и получатель.
* `cellRepository.getCounts()` — подсчёт ячеек по состояниям одним запросом;
  `cellRepository.findActiveOrder()` — заказ в ячейке вместе с получателем.

**Страница «Ячейки хранения»**
* `src/views/cellsPage.js`, `public/js/cells.js` — страница `/cells` вместо
  заглушки «в разработке»: показатели склада, сетка ячеек (свободные —
  зелёная полоса, занятые — оранжевая), фильтр «Все / Свободные / Занятые»,
  кнопка обновления. Администратор видит трек-номера и по нажатию
  на ячейку — сведения о заказе.
* Методы `freeCells()`, `cellsSummary()`, `cell(id)` в `public/js/api.js`.

**Проверка и документация**
* `scripts/check-v0.11.js` — автоматическая проверка сборки по 36 контрольным
  точкам: состояние склада проверяется до и после размещения заказов.
* `tests/cellsApi.test.js` — 15 тестов API ячеек и страницы.

### Изменено

* Клиент больше не получает трек-номера чужих заказов: параметр
  `withOrders=true` учитывается только для администратора.
* Идентификатор ячейки в адресе проверяется: `/api/cells/abc` возвращает
  `400` с понятным сообщением вместо «ячейка NaN не найдена».
* Ответы раздела `/api/cells` не кешируются браузером (`Cache-Control: no-store`).

### Технические решения

* Сводка считается одним SQL-запросом с условными суммами: свободные
  и занятые ячейки подсчитываются в один момент, поэтому их сумма всегда
  равна общему числу.
* Адреса `/free` и `/summary` объявлены раньше `/:id`: иначе Express
  принял бы слово «free» за идентификатор ячейки.
* Разметка плиток на странице создаётся через `createElement` и
  `textContent`, а не через `innerHTML`: данные из базы не могут
  внедрить код на страницу.

## [0.10.0] — 11-й день практики

### Добавлено

**Переключатель темы оформления**
* `public/js/theme.js` — модуль темы: три режима (светлая, тёмная, как
  в системе), чтение и сохранение выбора в `localStorage` (ключ `pvh.theme`),
  определение темы операционной системы. Подключается в `<head>` без `defer`
  и до таблицы стилей, поэтому тема применяется до отрисовки страницы.
* Кнопка в шапке переключает режимы по кругу: светлая → тёмная → как в системе.
  Подсказка на кнопке называет текущий режим и тот, что включится по нажатию;
  смена темы объявляется программам чтения с экрана.
* Выбор, сделанный в одной вкладке, сразу применяется в остальных (событие
  `storage`). В режиме «как в системе» тема меняется вслед за настройкой
  системы без перезагрузки.
* Плавная смена цветов при переключении (класс `theme-transition` на 300 мс);
  при системной настройке «уменьшить движение» тема меняется мгновенно.

**Проверка и документация**
* `scripts/check-v0.10.js` — автоматическая проверка сборки по 34 контрольным
  точкам, включая перезагрузку страницы в модели браузера.
* `tests/theme.test.js` — 21 тест: режимы темы, кнопка, синхронизация вкладок,
  отсутствие мерцания, контраст цветов, исправления замечаний.
* Команда `npm run check:v09` для проверки сборки 10-го дня.

### Исправлено (замечания к сборке v0.9)

* Индикатор надёжности пароля на странице регистрации не появлялся: сценарий
  искал оценку в полях, которых нет в ответе сервера. Теперь оценка берётся
  из поля `strength` ответа `POST /api/password/strength`.
* Кнопки «Показать пароль» на страницах входа и регистрации не работали:
  обработчик подключался только на странице проверки шаблона. Теперь все
  кнопки подключаются общим сценарием `layout.js`.
* На странице результата подтверждения кнопка «Получить новое письмо» вела
  на несуществующий адрес `/resend-confirmation.html`. Теперь она ведёт
  на страницу `/confirm` с формой повторной отправки.
* Карточки «Мои заказы» и «Ячейки» на главной странице вели на адреса
  `/orders.html` и `/cells.html`, которые отдавали 404. Ссылки исправлены,
  старые адреса перенаправляются.

### Изменено

* Цвет предупреждений светлой темы затемнён (`#b26a00` → `#995c00`):
  прежний давал контраст 3,9:1 при рекомендуемых 4,5:1.
* Текст кнопки удаления в тёмной теме сделан тёмным (переменная
  `--color-danger-contrast`): белый на светло-красном давал контраст 2,4:1.
* В тёмную тему по настройке системы добавлены тени, как и в явно
  выбранной тёмной теме.

### Технические решения

* Тема применяется сценарием в `<head>`, а не после загрузки страницы.
  Сценарий с `defer` выполнился бы после отрисовки, и при каждом переходе
  мелькала бы светлая тема.
* Атрибут `data-theme` хранит фактическую тему (по нему работает таблица
  стилей), `data-theme-mode` — выбор пользователя. Благодаря этому режим
  «как в системе» отличается от явно выбранной темы, совпадающей с системной.
* Контраст цветов проверяется тестом по формуле WCAG 2.1: при изменении
  палитры нечитаемое сочетание будет обнаружено автоматически.

## [0.9.1] — исправление отправки почты и запуск в Docker

### Исправлено

* **Интерфейс сообщал об отправке письма, когда письмо не отправлялось.**
  Режим `log` (письмо выводится в журнал сервера и никуда не уходит) считался
  успешной отправкой, поэтому после регистрации выводилось сообщение
  «на адрес … отправлено письмо», хотя почтовый ящик оставался пустым.
  Теперь поле `sent` означает именно доставку на почтовый сервер, добавлено
  отдельное поле `logged`, а сообщения на страницах регистрации, входа
  и подтверждения различают три случая: письмо доставлено, отправка
  не настроена, отправка не удалась.

### Добавлено

* Запуск проекта в контейнерах: `Dockerfile`, `docker-compose.yml`,
  сценарий запуска `docker-entrypoint.sh`. Приложение поднимается одной
  командой `docker compose up -d --build`; миграции и начальные данные
  применяются автоматически.
* Перехватчик писем **mailpit** в составе `docker-compose.yml`: принимает
  письма по SMTP и показывает их в браузере по адресу http://127.0.0.1:8025.
  Позволяет проверять регистрацию и подтверждение адреса, не заводя
  почтовый ящик.
* `scripts/check-docker-mail.js` — проверка отправки писем в контейнере
  по 15 контрольным точкам: регистрация, приём письма почтовым сервером,
  переход по ссылке из письма, повторное использование ссылки, вход.
* `.env.docker.example` — образец настроек для контейнеров, включая готовый
  блок для Gmail.

### Изменено

* Диагностика `npm run mail:check` определяет, что почтовый сервер требует
  вход (код 530), и подсказывает причину отказа по коду ответа: 530 — не
  указан логин, 535 — неверный пароль или обычный пароль вместо пароля
  приложения. Дополнительно проверяется, что адрес отправителя не вымышленный
  и совпадает с логином.

### Технические решения

* **Сценарий запуска контейнера выравнивает права на каталог данных.**
  Каталог `data` подключается как том, поэтому его содержимое может
  принадлежать суперпользователю; в этом случае SQLite возвращал ошибку
  «attempt to write a readonly database». Сценарий выполняется
  от суперпользователя, исправляет владельца каталога и запускает
  приложение от непривилегированной учётной записи `node` через `setpriv`
  из состава `util-linux` (входит в базовый образ, дополнительных пакетов
  не требуется).
* Зависимости в образе ставятся через pnpm со строгой фиксацией версий
  из `pnpm-lock.yaml`: структура каталога `node_modules` задаётся параметром
  `nodeLinker: hoisted`, поэтому символических ссылок не возникает.
* В `docker-compose.yml` настройки почты заданы значениями по умолчанию
  и указывают на перехватчик mailpit. Для реальной отправки достаточно
  подключить файл `.env.docker` одной строкой `env_file`: значения из него
  переопределяют переменные по умолчанию, правка самого файла
  `docker-compose.yml` не требуется.
* `docker compose` читает файл `.env` для подстановки значений
  в `docker-compose.yml`. Поскольку в этом файле указан режим `log`, настройки
  почты в `docker-compose.yml` заданы явными значениями, а не через
  подстановку: иначе переменные из `.env` перекрывали бы настройки
  перехватчика.
* Средство смены пользователя выбрано по фактическому составу образа:
  `gosu` в `node:22-slim` отсутствует, поэтому применяется `setpriv`
  из состава `util-linux`.

## [0.9.0] — 10-й день практики

### Добавлено

**Страницы регистрации и входа**
* `src/views/authPages.js` — разметка страниц учётной записи:
  регистрация, вход, результат подтверждения адреса, «страница не найдена».
  Все страницы отдаются в общем шаблоне, поэтому шапка, меню и подвал
  описаны один раз.
* `src/routes/pages.js` — маршруты страниц: `/`, `/register`, `/login`,
  `/confirm`, `/template-demo`. Адреса с расширением (`/login.html`
  и подобные) перенаправляются на страницы приложения.

**Клиентские модули**
* `public/js/api.js` — обращения к REST API: единое формирование запросов,
  обработка ошибок сервера с понятными сообщениями, ограничение времени
  ожидания ответа.
* `public/js/form.js` — проверка полей формы по правилам, совпадающим
  с серверными: обязательность, длина, формат адреса электронной почты,
  сложность пароля, совпадение пароля и его повтора. Сообщения выводятся
  рядом с соответствующим полем.
* `public/js/register.js` — сценарий страницы регистрации: проверка полей,
  индикатор надёжности пароля, отправка запроса, переход на страницу входа
  с сообщением об успехе.
* `public/js/login.js` — сценарий страницы входа: отправка запроса,
  переход на запрошенную страницу, отдельная обработка случая
  неподтверждённого адреса с предложением запросить письмо повторно.
* `public/js/confirm.js` — сценарий страницы подтверждения адреса.

**Проверка и документация**
* `scripts/check-v0.9.js` — автоматическая проверка сборки по 60 контрольным
  точкам: вся цепочка от страницы регистрации до выхода из системы.
* `tests/authPages.test.js` — 26 тестов страниц учётной записи.
* `tests/formValidation.test.js` — 27 тестов проверки полей в браузере,
  включая сверку правил с серверными.

### Изменено

* Версия сборки повышена до 0.9.0; `npm run check` выполняет проверку текущей
  сборки, проверки предыдущих дней доступны командами `npm run check:v01` …
  `npm run check:v08`.
* Справка о разделах API переведена с адреса `/` на `/api`: по корневому
  адресу теперь открывается главная страница приложения.
* Подтверждение адреса по ссылке из письма выполняется адресом
  `/api/auth/confirm/page`, который перенаправляет пользователя на страницу
  результата. Прежний адрес `/api/auth/confirm` сохранён для программных
  клиентов и отдаёт результат в формате JSON.
* Формат ответа для ненайденного адреса зависит от запроса: браузер получает
  оформленную страницу, программа — ответ в формате JSON.

### Технические решения

* Разметка страниц формируется на сервере. Благодаря этому при отключённых
  сценариях пользователь видит осмысленную страницу, а сведения о нём
  и его роли подставляются сразу, без дополнительного запроса к API.
* Проверка полей выполняется и в браузере, и на сервере. Первая нужна для
  удобства (ошибка видна сразу), вторая — для защиты: запрос можно отправить
  в обход браузера. Правила и тексты сообщений в обоих случаях совпадают,
  что проверяется отдельным тестом.
* Адрес возврата после входа (`next`) проверяется: принимаются только
  внутренние адреса. Иначе форму входа можно было бы использовать для
  перенаправления пользователя на сторонний сайт.
* Тексты сообщений на странице подтверждения не подставляются из параметров
  запроса напрямую: параметр `status` отображается на заранее заданный набор
  сообщений. Произвольное значение из адреса не попадает в разметку.
* Cookie с токеном сессии имеет флаг `HttpOnly`, поэтому сценарии браузера
  не имеют к нему доступа. Выход из системы выполняется запросом к серверу,
  а cookie передаётся автоматически.

## [0.8.0] — 9-й день практики

### Добавлено

**Базовый адаптивный шаблон**
* `src/views/layout.js` — шаблон страницы: шапка с наименованием, меню
  и элементами управления, подвал со сведениями о проекте. Состав меню
  зависит от роли пользователя.
* `src/routes/pages.js` — отдача страниц приложения; главная страница
  и страница проверки элементов оформления (`/template-demo`).
* `public/css/main.css` — единая таблица стилей на переменных оформления:
  светлая и тёмная темы, сетки, кнопки, формы, уведомления, таблицы,
  карточки, шапка, подвал, стили для печати.
* `public/js/layout.js` — общие сценарии интерфейса: переключение темы
  с сохранением выбора, меню на мобильных устройствах, уведомления,
  переключение видимости пароля, выход из системы.

**Проверка и документация**
* `scripts/check-v0.8.js` — автоматическая проверка сборки по 57 контрольным
  точкам.
* `tests/layout.test.js` — 27 тестов базового шаблона.

### Изменено

* Версия сборки повышена до 0.8.0.
* Корневой маршрут `/` отдаёт HTML-страницу приложения; справка о разделах
  API перенесена на адрес `/api`.

### Технические решения

* Вёрстка построена по принципу «сначала мобильные устройства»:
  оформление рассчитано на узкий экран, а для широких экранов добавляются
  правила, расширяющие макет.
* Минимальный размер интерактивных элементов задан равным 44 точкам —
  рекомендация по доступности для сенсорных экранов.
* При вёрстке учтены требования доступности: смысловая разметка (header,
  nav, main, footer), ссылка перехода к содержимому, подписи элементов
  управления для программ чтения с экрана, состояние кнопок в атрибутах
  `aria-expanded` и `aria-pressed`, отключение анимации при соответствующей
  настройке системы.
* Роль пользователя записывается в атрибут `data-role` элемента `body`,
  поэтому разделы администратора скрыты даже при отключённых сценариях.

* Проверки доступа разделены по смыслу: `requireAuth()` возвращает `401`
  (сессия отсутствует, не найдена или истекла), `requireRole()` — `403`
  (пользователь определён, но прав недостаточно). Порядок проверок задан
  явно, поэтому клиент, вошедший в систему, получает понятное сообщение
  «Недостаточно прав», а не «Требуется авторизация».
* Ссылочная целостность при удалении ячейки проверяется в сервисе до обращения
  к базе данных: пользователь получает сообщение с количеством связанных
  заказов, а не техническую ошибку ограничения внешнего ключа.
* Ячейку с активным заказом нельзя перевести в состояние «Свободна»: иначе
  заказ остался бы привязанным к свободной ячейке и её можно было бы занять
  повторно. Для освобождения требуется оформить выдачу заказа.
* При добавлении ячейки номер можно не указывать — он вычисляется как
  следующий за наибольшим существующим. Это исключает случайное совпадение
  номеров при добавлении ячеек через интерфейс.

* **Изменён порядок хранения результатов работы.** Исходный код ведётся только
  в основном каталоге проекта; копии проекта в каталоги отчётов по дням больше
  не создаются. Состояние кода на конец любого дня доступно из истории Git
  командой `git checkout <тег>`. Сценарий `archive-day.js` заменён на
  `finish-day.js`, который проверяет готовность дня (коммит и наличие отчёта).
* В каталоге отчётов создан отчёт за 1-й день (ранее он отсутствовал).

### Технические решения

* Сессии реализованы как записи в базе данных с непрозрачными токенами,
  а не как подписанные токены (JWT). Преимущество: сессию можно немедленно
  завершить — например, при выходе из системы или смене пароля. Подписанный
  токен оставался бы действительным до истечения срока.
* При неверном адресе электронной почты и при неверном пароле возвращается
  **одно и то же сообщение**. Иначе по тексту ошибки можно было бы определить,
  какие адреса зарегистрированы в системе.
* Проверка пароля выполняется даже для несуществующего пользователя (с заведомо
  неверным хешем), чтобы время ответа не позволяло определить наличие адреса.
* Токен хранится в cookie с флагом `HttpOnly`: клиентский сценарий не имеет
  доступа к токену, что защищает от его кражи через внедрённый код.
* После смены пароля завершаются все прочие сессии: если пароль изменён
  из-за подозрения на компрометацию, доступ по старым токенам прекращается.

* Записи, у которых дата формирования токена не заполнена (созданные
  до появления поля), считаются действующими: иначе пользователи,

* Ожидаемые ситуации (истёкший срок, недействительный токен) не выбрасывают

* SMTP-клиент реализован самостоятельно, а не через библиотеку `nodemailer`:

  библиотека добавляет десятки зависимостей. Это упрощает развёртывание проекта
  и делает весь код отправки проверяемым.
* Тело письма кодируется в base64, а не в quoted-printable: кодирование проще,

* Подтверждение адреса проверяется на настоящем SMTP-сервере, поднятом

* `docs/postman/PVZ-Password-Day4.postman_collection.json` — коллекция из 7 запросов
  с автоматическими проверками.

### Изменено

* Версия сборки повышена до 0.3.0; `npm run check` выполняет проверку текущей
  сборки, проверки предыдущих дней доступны командами `npm run check:v01`
  и `npm run check:v02`.
* `userRepository.toPublic()` теперь удаляет и хеш пароля, и токен подтверждения:
  ранее хеш мог попасть в ответ сервиса.
* Проверка пароля на личные данные перенесена в сервисный слой: при смене пароля
  имя и адрес берутся из записи пользователя, а не из формы.

### Технические решения

* Оценка надёжности построена на штрафах за конкретные недостатки, а не на едином
  регулярном выражении: это позволяет объяснить пользователю, что именно следует
  исправить, и подготовить основу для индикатора надёжности в интерфейсе (10-й день).
* Словарь ненадёжных паролей хранится в нормализованном виде, а сравнение
  выполняется по нескольким вариантам написания — это позволяет распознавать
  пароли вида «Qwerty_123», «P@ssw0rd», «qwerty2026» без увеличения словаря.
* Маршрут смены пароля `POST /api/password/change` будет подключён на 7-м дне,
  после реализации авторизации: до этого момента операция недоступна по HTTP,
  так как изменять пароль без подтверждения личности небезопасно.

* Версия сборки повышена до 0.2.0; сценарий `npm run check` выполняет проверку
  текущей сборки, проверка 2-го дня доступна командой `npm run check:v01`.
* Пределы частоты запросов вынесены в переменные окружения
  `RATE_LIMIT_WINDOW_MS` и `RATE_LIMIT_MAX`.

### Технические решения

* Для хеширования выбран `scrypt` из встроенного модуля `node:crypto`, а не
  библиотеки `bcrypt` или `argon2`: они требуют компиляции нативных модулей,
  что усложнило бы развёртывание проекта на другом компьютере.
* Ограничение частоты запросов реализовано в памяти процесса без внешнего
  хранилища: для учебного проекта этого достаточно. При развёртывании на
  нескольких серверах потребовалось бы общее хранилище (например, Redis).

### Технические решения
